# Exit and risk research plan (research only)

**Status:** protocol, not a live strategy change. The Cloud Run Job, OANDA practice orders, X posts, `config/strategy.yml`, and deployment are unchanged. The objective is to find out whether a simpler exit policy improves **net** return and drawdown for the *existing* 09:30–10:00 NY opening range / 10:22 decision / noon exit. There is no guaranteed profitable rule.

## Starting evidence and caveats (checked 2026-09-26)

- Current rule: **25-point stop / 75-point target**, approximately **$80 per point** for the configured position. The target is 75 **points**, not $80. From the Cloud Run session summaries visible for 2026-08-27 through 2026-09-25: 22 sessions, 20 orders, 4 profitable trade days, 16 losing trade days, aggregate reported balance change **−$13,536**. Of those losses, eight had logged estimated MFE >= 20 points, and three reached >= 40 points (Sep 17, 22, 24). The other eight losses never logged +20, so earlier profit-taking alone cannot fix them; a +40 target also sacrifices part of the +75 winners. This is a *small, recently observed, selected window*, not an unbiased estimate of future returns or a backtest of a 40-point target.
- MFE/MAE and some exit reasons in `opening_range_bot/run_bot.py` come from `simulate_exit()` on one-minute **mid** candles, **not** the broker's closing transactions. For a broker-closed trade the bot can log `TIME` even though the account lost on its stop. Candle highs do not prove an executable bid/ask limit fill; bar ordering can be ambiguous. Cloud Logging contains summaries but the `daily_json` with `trade_path_candles` is written to an ephemeral Cloud Run filesystem. Intermittent 401/timeouts are visible in logs.
- **Prior backtest integrity blocker (code corrected in step 2, historical results not reproduced):** `notebooks/04_parameter_robustness.ipynb` previously tried to override nonexistent `STRATEGY["rules"]["risk"]["sl_points"/"tp_points"]`, whereas `config/strategy.yml` uses `parameters.risk.stop_loss_points/take_profit_points`. `src/or_core.py` had import-time risk constants and no per-call overrides; the entry sweep mutated `or_core.ENTRY_T` without restoring it, so subsequent labeled sweeps could repeat baseline risk/zones at the last entry time. Explicit arguments and synthetic parameter-effect tests now replace that path; stale notebook outputs have been cleared. **Do not trust old sweep rankings or claim an optimum until the original raw data have been rerun.** Notebook 3's historical summaries likewise need reproduction; no original 2020–2024 CSVs are available in this checkout.
- `config/instruments.yml` names `NSXUSD` for historical CSV research, whereas the OANDA runtime uses `NAS100_USD`. Verify point, contract/unit, bid/ask, calendar, timezone, and price-series comparability before combining histories.

## Phase 1 — Fix the simulator before optimizing it

- One reusable, pure function accepts an explicit `StrategyParams` and an immutable market path: baseline SL=25, TP=75, original signal/no-trade logic and noon flat. Backtest and replay call the same policy/evaluation logic; no notebook global mutations or cached risk constants. Add synthetic tests that changing **each** SL, TP, zone, and entry-time parameter changes the appropriate outcome; unchanged candidates should fail validation. Freeze this harness/version before evaluating results.
- Simulate an order *after the 10:22 bar is complete*; research starts from the broker's actual fill and timestamps when reconciling paper trades. Verify how a 10:22 candle close, 10:23 execution, broker-attached distance orders, and historical CSV timestamps differ. Anchor price levels to the actual fill, not just signal close.
- For any minute when TP, SL, trailing/updated stop, or partial fill could all occur, assume **adverse sequencing** if only OHLC is known; separately report a best-case bound and the percentage of ambiguous days. Reconcile bid/ask, slippage, gaps, stop-market vs limit semantics, partial-size rounding, transaction fees, 12:00 close and missing candles. If ambiguity determines the winner, acquire finer data or call the result inconclusive.
- Compare the simulated **baseline** with practice fills day-by-day, not just total P&L. Explain differences, reproduce cost assumptions, then rerun original research notebooks/sweeps with verified data. Do not treat the existing 2022–2024 notebook results as pristine holdout data after they have been viewed during prior tuning.

**Gate:** zero *unexplained* baseline mismatches on complete reconcilable paper days; all excluded/ambiguous days counted; explicit parameter-effect tests pass.

## Phase 2 — Diagnose the failure mode without optimizing on 20 days

Create per-trade and per-signal-day tables: broker P&L; signed mark-to-market at +10/+20/+30/+40/+50/+75; **first-hit time** for each executable threshold; MFE/MAE *through actual exit*; time spent in profit; retracement before SL or noon; entry spread, OR width, pre-entry volatility and hour. Separate early-stop trades (never reached +20) from give-backs (threshold touched then loss) and compare long/short, year and volatility regime. If early stops dominate, prioritize a *separate* entry-quality/volatility/spread-filter hypothesis rather than forcing exit tuning to solve an entry problem. Report execution/spread and missingness. The 20 recent trades are a diagnostic case study, **not** the training set for a finely tuned threshold.

## Phase 3 — Predeclare a small exit-policy matrix

`research/experiments.yml` predeclares the **first pass**. Protocol v2, revised before the first candidate run, names explicit modeled cost scenarios and sample-size gates without changing target levels. Same eligible signal days, same entry, same 25-point initial stop, same unit exposure, same noon flat and common transaction-cost scenarios for all candidates:

| Family | Initial variants to compare | Trade-off / failure to watch |
| --- | --- | --- |
| Control | Entire position TP +75 | Benchmark, not assumed optimal. |
| Simpler fixed targets | Entire position TP +40 or +50 | More frequent small wins but truncate large wins; may not improve expectancy. |
| Partial take-profit | 50% at +30 or +40, remainder at +75, original stop | More exits/spread; unprotected remainder can still lose. |
| Profit protection | Activate stop at entry (gross breakeven, not net after costs) on first executable +30 or +40 touch; original +75 TP | Whipsaws, missed broker amendments, gaps and order-modification feasibility. |
| Simple trailing | Start at +40, trail by 20 points on remaining position; TP +75 | Path ambiguity and friction; cannot rely on 30-second polling alone. |
| Time-based | If still open at 11:15 NY, close at executable market price | May cut profitable late moves; compare on all signal days. |

Do **not** combine every threshold/fraction/trail into an unbounded grid. A partial at +30 followed by a −25 stop on the other half nets only **+2.5 points gross** (0.5×30 − 0.5×25), before spread/fees; partial fills do not automatically solve losses. For every rule model actual bid/ask, extra transactions, stop slippage, gaps and realistic OANDA order support. Broker-side protective orders must survive a process crash; no code in this plan submits, cancels or modifies orders.

**Exploratory, separate follow-up:** ATR-scaled target/stop or exit by realized volatility; entry-time momentum / EWMA trend; volatility-normalized size with a strict maximum 25-point-equivalent account risk. Signal features must use only data available **at** the decision, exit features only data available **before** their order update. Keep size effects separate from exit effects. These variants require enough independent data to justify extra degrees of freedom.

### Adam / RMSProp analogy

Adam and RMSProp smooth **past gradients to optimize model parameters**. They are not automatic profit-taking rules and cannot turn a noisy 20-trade sequence into a reliable gradient. The useful analogue is a predeclared **causal EWMA of price trend or volatility** to decide whether to let an already-profitable runner continue, or a volatility-scaled risk budget. Test it *after* simple fixed/partial rules, without tuning on the evaluation period. If ever adapting parameters between days, use only previous days' data, freeze the update schedule and hard-cap risk; no online optimizer learning from today's eventual exit. Discrete fills and stop/target hits are path-dependent and not a smooth differentiable loss for Adam.

## Phase 4 — Validation, uncertainty, and selection

1. **Historical development:** reproduce existing 2020–2024 baseline first; use rolling-origin chronological train → next contiguous validation block, frozen parameters per block. Prior notebook inspection contaminated any nominal 2022–2024 holdout; label it as development, not independent confirmation. Reserve genuinely unseen future practice sessions as prospective holdout. Track no-trade days and data exclusions for every candidate.
2. **Primary comparison:** *paired* difference in **net P&L per eligible session** (including no-trade days), candidate minus baseline. Also report mean net P&L per actual trade, profit factor (with finite denominator), max peak-to-trough drawdown, worst week, CVaR/tail daily loss, trade count, hit rate, exposure and number/cost of broker amendments. Report both points and USD under the same size/fees; no Sharpe/annualized inference from 20 trades.
3. **Monte Carlo (uncertainty, not an alpha generator):** resample *paired daily paths* in contiguous **week-sized or longer blocks**, preserving no-trade days and serial dependence; run >= 2,000 fixed-seed draws at the same exposure. Show 5/50/95% paired net-improvement and drawdown quantiles, chance the candidate trails baseline, and chance of hitting a predeclared drawdown limit. A simple trade-order shuffle can illustrate path/drawdown risk but **cannot** establish better expected profit or correct selection bias. With very few independent blocks, intervals are unreliable: report that instead of a strong probability claim. Stress bid/ask, 2× spread/slippage, outages, adverse same-bar ordering, and year/regime leave-one-out.
4. **Multiple comparisons:** count every tried candidate (including later tweaks), keep a full experiment ledger, use a small predeclared family; do not select the best of many then quote its unadjusted backtest p-value. Prefer a broad parameter plateau and a simple rule over a single best threshold. Freeze candidate and analysis code before checking prospective paper sessions; no retuning on the held-out series. Literature: [White, *A Reality Check for Data Snooping* (2000)](https://users.ssc.wisc.edu/~behansen/718/White2000.pdf); [Bailey et al., *The Probability of Backtest Overfitting*](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf).

**Promotion gate (decision, not automatic deployment):** pass parity and data-quality gates; positive paired *net* improvement that survives conservative execution/cost stress and multiple-comparison scrutiny; no unacceptable drawdown increase; results reasonably stable across years/regimes; then a frozen, genuinely forward **paper** shadow test across enough new sessions to assess uncertainty. If inconclusive, keep 25/75 and collect more data. Any Cloud Run order changes require explicit approval, documented broker-side stops/partials, durable idempotency/restart handling, and no extra X posts during research.
